# 프로젝트 위키 작성 기준

## 목차

- 문서 계층과 파일명
- Frontmatter
- 조사 범위
- 페이지 구성
- 데이터와 상태 흐름
- 사실과 추론
- 문체와 구현 근거
- 완료 점검표

## 문서 계층과 파일명

기존 위키가 있으면 그 계층과 번호 체계를 유지한다. 새 위키는 프로젝트 규모에 맞춰 가장
작은 구조로 시작한다.

```text
프로젝트
├─ 00 인덱스
├─ 제품·업무 영역
│  └─ 화면·기능 상세
└─ 기술 영역
   └─ 아키텍처·API·데이터 상세
```

번호는 정렬이 필요할 때만 사용한다. 번호를 사용하는 위키에서는 `00`을 폴더 인덱스로 두고,
frontmatter의 `title`과 본문 H1에는 번호를 넣지 않는다.

## Frontmatter

기존 문서의 스키마를 우선한다. 새 위키의 기본 형식은 다음과 같다.

```yaml
---
title: 문서 제목
date: YYYY-MM-DD
tags: [프로젝트, 주제]
icon: 📄
status: draft
scope: 프로젝트 식별자
source_updated_at: YYYY-MM-DD
---
```

`source_updated_at`에는 마지막으로 구현과 대조한 날짜를 기록한다. `scope`가 필요 없는 저장소나
위키 시스템에서는 생략할 수 있다.

## 조사 범위

대상 기능에 실제로 존재하는 계층만 조사한다.

| 계층 | 확인할 내용 | 대표 검색 대상 |
| --- | --- | --- |
| 진입점 | 메뉴, 라우트, 명령, 권한 | route, menu, command, permission |
| 사용자 인터페이스 | 입력, 버튼 조건, 화면 검증 | component, view, form, validation |
| 클라이언트 로직 | 상태, 캐시, 요청 조합 | store, hook, query, mutation |
| API | 요청·응답, 인증, 오류 | endpoint, controller, DTO, schema |
| 도메인 로직 | 트랜잭션, 상태 전환, 제약 | service, use case, policy, event |
| 저장 계층 | 엔터티, 관계, 인덱스, 파일 | model, repository, migration, schema |
| 후속 소비 | 조회, 복제, 내보내기, 알림 | consumer, worker, export, webhook |

한 계층에서 확인한 식별자, 상태명과 필드명을 다음 계층의 검색어로 사용한다. 프레임워크나
데이터베이스 종류를 미리 가정하지 않는다.

## 페이지 구성

문서 유형에 맞는 항목만 포함한다.

### 인덱스

- 영역의 범위와 책임
- 하위 문서 목록과 설명
- 권장 탐색 순서
- 현재 문서화 범위
- 상위·인접 영역 링크

### 화면·기능

- 기능이 관리하는 대상
- 접근 조건과 권한
- 사용자가 수행하는 실제 순서
- 입력과 화면 검증
- 서버 검증과 저장 결과
- 완료 후 가능한 후속 작업
- 실패 조건과 복구 방법

### 아키텍처·데이터

- 주요 구성요소와 책임
- 기준 엔터티와 식별자
- 요청, 이벤트와 데이터 흐름
- 관계 타입과 참조 필드
- 캐시·복제·동기화 시점
- 변경과 삭제의 전파 범위
- 장애 경계와 재시도·복구 방식

## 데이터와 상태 흐름

설정값마다 다음 문장을 완성할 수 있을 때까지 추적한다.

> 사용자는 **어디에서** **어떤 값**을 설정한다. 시스템은 값을 **어디에서 검증**하고
> **어디에 저장**한다. **어떤 시점에** **어떤 후속 기능**이 값을 조회하거나 복제한다.
> 값을 바꾸거나 삭제하면 **기존 데이터와 신규 데이터에 어떤 영향**이 생긴다.

연결 방식은 코드에서 확인한 형태로 구분한다.

| 연결 방식 | 설명할 내용 |
| --- | --- |
| 식별자 연결 | ID나 키만 저장하고 원본을 다시 조회하는지 |
| 스냅샷 | 생성 시점의 값을 복사해 독립적으로 유지하는지 |
| 실시간 조회 | 사용할 때마다 최신 기준 데이터를 읽는지 |
| 비동기 전파 | 이벤트나 작업 큐가 나중에 반영하는지 |
| 신규 적용 | 변경 이후 생성되는 데이터에만 적용하는지 |

## 사실과 추론

- 코드, 테스트, 스키마와 공식 문서에서 확인한 내용은 현재 동작으로 서술한다.
- 여러 근거를 조합한 결론은 `추론`임을 표시하고 근거를 함께 남긴다.
- 비즈니스 정책을 확인할 수 없으면 임의로 완성하지 않고 `미확인`으로 기록한다.
- 화면 표시와 서버 검증이 다르면 각각의 동작과 적용 범위를 분리한다.
- 현재 기능에 영향을 주지 않는 폐기 코드와 구현 이력은 운영 위키에서 제외한다.

## 문체와 구현 근거

기능의 주체와 동작을 먼저 쓰고 중립적인 능동형 문장을 사용한다. 기능을 부정형 대조로
소개하지 말고 대상과 동작을 직접 설명한다. 실제 시스템 제약은 정확한 부정문으로 기록한다.

중간 제목은 `결제 승인 상태 전환`, `문서 저장과 검색 인덱스 갱신`처럼 대상과 관계 또는
처리를 함께 쓴다. `먼저 확인할 것`, `전체 흐름`, `알아둘 점`처럼 내용을 찾기 어려운 제목은
피한다.

`구현 근거`에는 다음 정보를 저장소 기준 상대 경로로 기록한다.

- 프런트엔드 또는 클라이언트 파일과 주요 컴포넌트
- 백엔드, 서비스 또는 작업 파일과 주요 심볼
- 확인한 스키마, 엔터티, 메시지 또는 관계 타입
- 동작을 보장하는 테스트 파일

## 완료 점검표

- 첫 문장이 제목의 대상을 직접 설명한다.
- 현재 구현을 기준으로 사용자 절차와 시스템 동작을 연결했다.
- 입력, 검증, 저장과 후속 소비 지점이 끊기지 않는다.
- 화면 검증과 서버 검증의 차이를 구분했다.
- 상태 전환·변경·삭제가 기존 데이터에 미치는 영향을 설명했다.
- 확인한 사실, 추론과 미확인 정책을 구분했다.
- 코드의 화면 라벨, 상태명, 필드명과 API 이름을 유지했다.
- 구현 근거와 내부 링크가 실제 대상을 가리킨다.
- 상위 인덱스와 직접 관련된 문서를 함께 갱신했다.
- frontmatter, H1, 코드 블록과 위키 링크 검증을 통과했다.
