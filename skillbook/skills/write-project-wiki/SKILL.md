# Write Project Wiki

프로젝트의 실제 구현을 근거로 독자가 다른 문서를 오가지 않아도 이해할 수 있는 위키를 작성한다.

## 작업 절차

1. 실행 컨텍스트의 분석 프로젝트 경로와 문서 저장 대상 경로를 확인한다. 사용자가 저장소
   내부 문서를 명시하지 않았다면 위키 산출물은 현재 노트 섹션에 저장한다.
2. 기존 위키가 있으면 상위 인덱스와 유사한 상세 문서 2개 이상을 읽어 frontmatter,
   파일명, 제목 깊이, 용어와 링크 형식을 따른다. 기존 기준이 없으면
   [references/wiki-writing-guide.md](references/wiki-writing-guide.md)의 기본 형식을 적용한다.
3. 대상 기능의 진입점에서 시작해 실제로 존재하는 계층만 추적한다. 화면, 클라이언트 상태,
   API, 서비스, 저장소, 데이터 모델, 이벤트와 후속 소비 지점을 코드 검색으로 연결한다.
4. 각 설정값과 상태 전환에 대해 입력 위치, 서버 검증, 저장 위치, 조회·복제·전파 시점,
   변경·삭제 영향을 확인한다. 기술 스택이나 저장소 종류는 코드에서 확인한 것만 기록한다.
5. 확인한 사실과 추론을 구분한다. 코드에서 확인할 수 없는 정책은 채우지 말고 미확인 항목과
   확인에 필요한 근거를 명시한다.
6. 목적과 역할, 선행 조건, 실제 절차, 데이터 관계, 완료 조건, 실패 조건, 변경 영향을 필요한
   만큼 포함한다. 비교에는 표를, 세 단계 이상의 흐름에는 작은 Mermaid 다이어그램을 사용한다.
7. 새 문서를 추가하면 상위 인덱스와 직접 관련된 문서를 함께 갱신한다. 구현 근거에는 저장소
   기준 상대 경로와 핵심 심볼을 기록하되 비밀값과 개인 정보는 넣지 않는다.

## 검증

기존 위키 형식을 우선 보존한다. 이 스킬의 기본 형식으로 작성했거나 Markdown 구조와 내부
링크를 검사할 때 다음 명령을 실행한다.

```bash
python3 "<스킬 디렉터리>/scripts/validate_wiki.py" "<위키 경로>"
```

새 위키에 기본 frontmatter를 강제하려면 `--require-frontmatter`를 추가한다. 오류를 모두
수정하고, 경고는 실제 제약을 설명하는 문장인지 확인한 뒤 필요한 경우 직접 서술로 고친다.
마지막으로 화면 라벨, 상태명, API 이름과 구현 근거 경로를 `rg`로 다시 대조한다.

완료 보고에는 작성·수정한 페이지, 새로 설명한 주요 연결, 미확인 항목과 검증 결과를 포함한다.
